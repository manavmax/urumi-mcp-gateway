What is in the box

Everything below is implemented on this branch and verified by the test suite and live checks.

Gateway

  • One MCP endpoint. Every upstream answers on POST /mcp.
  • Namespaced tools. woo__list_products, so servers never collide.
  • Failure isolation. Per-server timeouts, a circuit breaker and a health loop.
  • Stable tool lists. A slow upstream serves its last known tools, marked stale.

Store and tools

  • A real store. WooCommerce with a 12-product catalog and cash on delivery.
  • 8 store tools. Products, orders and images over the WooCommerce REST API.
  • Three servers. woo, time and notes prove aggregation across upstreams.
  • Cross-server replies. One chat prompt can span two servers in one answer.

Team and control

  • Per-user API keys. Hashed, shown once, revocable in a click.
  • Tool permissions. Admins restrict individual tools for the member role.
  • Audit log and admin trail. Every call attributed, every admin action recorded.
  • Chat as yourself. The agent calls tools with the signed-in user's permissions.

From zero to a tool call

Three steps, all in the dashboard. No YAML for day-to-day use.

  1. 01

    Register servers once

    The admin adds each MCP server with its URL and credentials. Credentials are encrypted at rest and never sent to a client.

  2. 02

    Issue keys

    Invite members, then create one API key per person or client. Keys are shown once and stored as argon2id hashes.

  3. 03

    Use it from any client

    One URL in any MCP client, or the built-in chat. Every call is permission-checked and audited under its caller.

How a tool call travels

A call enters through one endpoint, is checked and audited, then reaches the store with credentials the caller never sees.

Animation is off when your system asks for reduced motion.

Control without ceremony

The controls that matter for a team are one click each, and every change lands in a trail you can read later.

  • Revoke a key and the next call gets 401.
  • Disable a server and its tools vanish from every client's list.
  • Restrict a tool for members and it disappears for them everywhere, including chat.
  • Kill a pod and the other servers keep answering while the dashboard flags it.

Security posture, stated plainly

Two auth domains: your key opens the gateway, the gateway holds the upstream credentials. They never meet.

A member can

  • Call every tool not denied by policy, with their own key.
  • See their own keys, their own activity and the tools they may use.
  • Use chat, which acts with exactly their permissions.

A member cannot

  • See an upstream credential. Not in any API response, ever.
  • See another member's keys or activity.
  • Call a denied tool: rejected before any upstream contact, audited as permission_denied.
  • Manage servers, members or permissions.

Hashed keys

argon2id with a SHA lookup hash. Shown once at creation, never stored in the clear.

Server-side credentials

Fernet-encrypted in Postgres, injected at proxy time only.

SSRF guard

Upstream URLs validated at save and re-resolved at connect. Redirects are never followed.

Default-deny network

Every allow rule is explicit, selector-driven and values-fed. Throwaway probes are blocked.

Non-root containers

Explicit uids, all capabilities dropped, read-only roots where the image allows.

Login lockout

5 failures in 300 seconds per username and per IP, then 429. Transitions are audited.

One Helm chart, two worlds

The same chart deploys to a local kind cluster and to a single-node k3s VPS. Only values change.

What runs where

  • Public tier. Ingress, then the gateway, the dashboard and this landing page.
  • Private tier. The three MCP servers, WordPress with WooCommerce and MariaDB, Postgres.
  • State. Postgres keeps users, keys, servers and audit. MariaDB keeps the store.
  • Delivery. One umbrella chart, no Kustomize, upgrade in one line with automatic rollback.

helm upgrade --install urumi ./helm --timeout 15m --atomic rolls itself back on failure; helm rollback urumi returns to any revision. Rehearsed in docs/UPGRADE_ROLLBACK.md.
